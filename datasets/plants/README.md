# Plants by WebSphere Dataset

This directory contains the monolithic dataset and adapter for **Plants by WebSphere**, a classic IBM WebSphere sample application demonstrating standard Java EE patterns.

The original monolithic application is tracked as a Git submodule in the `sample.plantsbywebsphere/` directory.

## Structure
- `sample.plantsbywebsphere/`: Git submodule containing the monolithic source code.
- `dataset.py`: Python script utilizing `javalang` to traverse the Java source code, extract all class/method signatures, and locate the required `plants_kdm.xmi`. It outputs this structured data to `dataset.json`.
- `plants_kdm.xmi`: The KDM Code Model XMI generated by Eclipse MoDisco.

## Eclipse MoDisco Generation (Known Workarounds)

Legacy Java EE datasets are notoriously difficult for Eclipse MoDisco to parse. The ATL KDM transformer will routinely crash (`VMException: Cannot convert javaToKdm`) if method bodies are not fully resolved. 

If you attempt to generate the Call Graph XMI for this dataset, you must apply the following workarounds (note: these may still fail depending on your Eclipse environment):

### 1. Java 8 Configuration in Eclipse
The project uses an ancient Gradle wrapper (v5) which crashes on modern Java versions (Java 21). You must configure Eclipse Buildship to use Java 8:
1. Import the project as an **Existing Gradle Project**.
2. Right-click the project > **Properties > Gradle**.
3. Under **Java home**, check **Specific Java home** and point it to a Java 1.8 JDK installation (e.g., via SDKMAN).
4. Right-click the project > **Gradle > Refresh Gradle Project**. Ensure there are 0 compilation errors.

### 2. MoDisco Discovery Preferences
To capture method calls, you must force MoDisco to parse method bodies while ignoring unresolved dependencies:
1. Navigate to **Window > Preferences > MoDisco > Java > Discoverer**.
2. **CHECK** `Deep analysis` (Mandatory to parse method bodies / method calls).
3. **CHECK** `Ignore unresolved bindings` (Attempts to prevent ATL transformer crashes on missing Java EE libraries).
4. **CHECK** `Serialize all elements`.

### 3. Manual 2-Step XMI Generation
Running the 1-step KDM discoverer directly often causes `DanglingHREFException`. Bypass this by running it in two explicit stages:
1. Right-click the project > **Discovery > Discoverers > Discover Java Model from Java project**. (This creates `sample.plantsbywebsphere_java.xmi`).
2. Right-click the newly generated `_java.xmi` > **Discovery > Discoverers > Discover KDM Model from Java Model**.
3. Rename the final KDM output to `plants_kdm.xmi` and place it in this directory (`datasets/plants/`).

## Usage

Once the `plants_kdm.xmi` is in place, run the adapter script using `uv`:

```bash
uv run dataset.py
```

This will parse all Java files inside the repository and output the standardized `dataset.json` file.
